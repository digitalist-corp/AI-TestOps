## 2. [1순위] LangGraph 학습 루프

### 2-1. 목표 (완료 기준)

다음이 **한 바퀴** 돌고, **두 번째 비슷한 실패에서는 이전에 승인된 수정을 참고해 더 빨리·정확히 제안**해야 한다:

> 실패 실행 → 묶기 → 원인 분류 → (과거 성공 수정 조회) → 수정안 → 격리 재검증 → **사람 승인** → 반영 → 재실행 → 실패 수 측정 → 계속/정지

"테스트할수록 똑똑해진다"는 말의 실제 구현은 아래와 같다.
- LangGraph 자체는 학습하지 않는다.
- 사람이 승인한 수정을 **실패 유형(시그니처)과 함께 저장**한다.
- 다음 루프의 recall 노드가 그 기록을 찾아 수정 프롬프트에 예시로 넣는다.
- 분류 결과를 사람이 고치면 그것도 저장해서 다음 분류의 예시로 쓴다.
- 이 저장소가 쌓일수록 정확도가 올라가고, 이를 **측정해 화면에 보여 준다** (2-5).

### 2-2. 구조 (E-01 결정 그대로, `docs/langgraph-placement-decision.md`)

```
web ─▶ Spring api ─(루프 시작·재개)─▶ ai-service (Python, LangGraph, 프로파일 ai)
          ▲  ▲                             │
          │  └── MCP tools/list · tools/call ┤  도구 (스키마는 Spring 한 곳)
          └──── /internal/ai-jobs/{id}/llm ──┘  LLM (키는 Spring에만)
                     PostgreSQL ◀── PostgresSaver (스키마 langgraph)
```

- LLM 호출은 Spring 프록시를 통해서만 한다 (컨테이너는 API 키를 보지 않는다).
- 파일 반영은 `AiJobService.applyDiff` 한 곳에서만 한다. `ApprovalGateInventoryTest`가 이를 지킨다.
- 승인은 그래프의 `interrupt()`로 멈추고, Spring의 AI 작업 카드에서 승인하면 Spring이 `Command(resume=...)`로 재개시킨다.
- **막히면 전환한다.** 11/19(목) 정오까지 E-03 · E-02 스모크가 안 되면 3안(LangGraph4j, Spring 내부)으로 바꾼다. 노드 설계는 그대로 둔다.

### 2-3. 작업 순서

| 순서 | ID | 작업 | 완료 조건 |
|---|---|---|---|
| 1 | E-03 | `apps/ai-service` 뼈대: Python 3.12 + langgraph + langgraph-checkpoint-postgres, `docker-compose.dev.yml`에 프로파일 `ai` | 빈 그래프가 체크포인트를 남기며 한 바퀴 돎 |
| 2 | E-02 | Spring `/mcp` (MCP Java SDK 코어. 막히면 initialize · tools/list · tools/call만 받는 JSON-RPC 컨트롤러). 작업 토큰(`ai_jobs.callback_token`)으로 인증, **허용 목록 도구만** 공개, 파일 쓰기 도구 금지 | ai-service가 `list_executions`를 불러 결과를 받음 |
| 3 | E-04 | ingest · cluster: 실패 실행의 단계 기록(1차 리포터) · 오류 메시지를 정규화해 **시그니처**로 묶기 | 실패 10건이 유형별로 묶임 |
| 4 | E-05 | classify: 테스트 문제 / 앱 버그 / 환경. 원인을 아는 평가셋 20건(`docs/eval/`) | 정확도 측정값이 나옴 (목표 70%) |
| 5 | **신규** | **학습 저장소 (V21)**: `ai_fix_memory`(시그니처, 분류, 실패 단계, 승인된 diff 요약, 결과 성공 여부, 승인자, 시각), `ai_classify_feedback`(시그니처, AI 분류, 사람 수정 분류) | 승인 · 분류 수정 시 자동 저장 |
| 6 | E-06 | recall · fix · 재검증: 같은 · 비슷한 시그니처의 성공 수정 상위 3건을 프롬프트에 넣음, 격리 러너에서 재검증 통과한 수정안만 다음 단계로 | 재검증 실패 수정안은 사람에게 안 감 |
| 7 | E-07 | 승인 interrupt · 재개: 승인 대기 중 서버를 재시작해도 이어짐 | 재시작 재개 테스트 |
| 8 | E-09 | measure · decide: 수정 전후 실패 수, 정지 조건(최대 3회 반복 · 비용 예산 · 정체 2회) | 정지 조건에서 멈추고 사람에게 넘김 |
| 9 | E-10 · E-11 | 노드 단계 상태를 DB에 기록 + 조회 API, **루프 타임라인 화면**(현재 노드 · 승인 대기 · 참고한 과거 수정 표시) | 진행 중인 루프의 단계가 보임 |
| 10 | E-08 | (여유) PR 생성: `ai/{jobId}` 브랜치만, main 직접 반영 0건 | 시간이 남을 때만 |

### 2-4. 화면

- 실패한 실행·결함 화면에 **"AI 루프로 고치기"** 버튼을 둔다 (PM 이상).
- 프로파일 `ai`가 꺼져 있으면 버튼을 숨기거나 비활성화하고 안내 문구를 보여 준다.
- 루프 타임라인: 노드 순서, 현재 위치, 승인 버튼(기존 AI 작업 카드 재사용), **"과거 수정 N건 참고"** 표시.

### 2-5. "똑똑해짐" 보여 주기 (발표용 지표)

- 대시보드에 다음 3가지를 추가한다 (계획서 G-02와 같은 데이터):
  - 학습 저장소 건수
  - 분류 정확도 추이
  - 수정안 첫 승인율 추이
- 시연용 시나리오: 같은 유형 실패 두 번 → 두 번째 루프에서 "과거 수정 1건 참고"가 뜨고 바로 맞는 수정안이 나오는 것.

## 3. [2순위] 개선 묶음

### 3-1. 보안 · 역할 (금요일 전 필수)

- [ ] **관리자 기본 비밀번호 admin/admin 제거**
  - `.env.example` · `DataLoader` 기본값이 admin이다.
  - 값이 비었거나 기본값이면 첫 로그인 때 비밀번호 변경을 강제한다 (변경 전 다른 API는 403).
  - 배포 서버가 기본값인지 확인하는 방법을 알려 준다 (값은 출력 금지).
- [ ] 로그인 칸에 값이 미리 채워진 것처럼 보이는 문제
  - 앱이 채우는 게 아니라 브라우저의 저장된 비밀번호다.
  - `autocomplete="username"` / `"current-password"`만 두고, 앱이 넣는 기본값이 없는지 테스트로 고정한다.
- [ ] **AI 키 관리자 전용 고정**
  - 서버는 이미 `/api/admin/` 아래라 막혀 있다.
  - PM·팀원이 AI 제공자 설정 조회·수정 시 403을 받는 통합 테스트를 추가한다.
  - 헤더의 "AI" 켜기·끄기 버튼이 무엇을 바꾸는지 확인하고, 팀원에게 필요 없으면 숨긴다.
- [ ] **공지사항 관리**: 표 형태, 전체 선택 · 일괄 삭제 · 일괄 고정/해제, 게시 기간 필터 (관리자만).
- [ ] 역할별 홈을 더 분명하게 나눈다.
  - 관리자: 사용자 · 러너 · 전체 진척
  - PM: 담당 프로젝트 진척 · 담당자별 · 승인 대기
  - 팀원: 나에게 배정된 항목 · 오늘 할 일
- [ ] 시연 데이터 정리
  - example.com 프로젝트 상태를 "실행"으로 바꾼다 (지금은 진척 80%인데 "계획"으로 보인다).
  - 게스트 알림이 9+로 쌓이지 않게 한다.
  - `scripts/demo-reset.sh`에도 반영한다.
