# 개발 계획서 1. 코드베이스 분석

2026-10-08 · aQm

## 1. 방향

AI가 테스트를 만들기 전에 **대상 서비스의 저장소 코드를 먼저 읽게 한다.** 지금은 URL과 요구사항 문장만 보고 셀렉터를 추측해서, 처음 만든 테스트가 자주 실패한다.

- **저장소 코드 분석을 먼저 만든다.** 화면 관련 파일을 규칙으로 추리고, LLM이 그 파일을 읽어 화면과 요소를 뽑는다.
- **사이트 탐색(URL을 열어 화면을 살피는 기능)은 뒤로 미룬다.** 없애지 않는다. 이미 만든 `analyze.js`는 그대로 두고, 코드 분석이 자리 잡은 뒤에 붙인다.
- 처음에는 **React Router와 Next.js** 프로젝트만 지원한다.

## 2. 처리 흐름

| 순서 | 하는 일 | LLM |
|------|---------|-----|
| 1 | 저장소를 복제하고 커밋 번호를 기록한다 | – |
| 2 | 규칙으로 화면(라우트)과 그 화면의 파일을 찾는다 | – |
| 3 | 화면 파일을 읽어 요소(버튼, 입력, 링크)를 뽑는다 | 사용 |
| 4 | 뽑은 속성으로 셀렉터를 만든다 | – |
| 5 | 화면과 전환을 DB에 저장한다 | – |
| 6 | 테스트를 만들 때 저장된 화면 정보를 AI에 넘긴다 | 사용 |

지켜야 할 것 세 가지.

- **셀렉터는 코드가 만든다.** LLM은 코드에 적힌 속성(`data-testid`, 라벨, 버튼 글자)만 알려 주고, 그 글자가 실제 파일에 있는지 확인해서 없으면 버린다. 지어낸 셀렉터를 막기 위해서다.
- **바뀐 파일만 다시 읽는다.** 파일 내용이 같으면 LLM을 다시 부르지 않는다.
- **저장소의 코드는 읽기만 한다.** 실행하거나 설치하지 않는다.

## 3. 저장 구조 (3단계)

분석 결과는 PostgreSQL에 3단계로 저장한다.

| 단계 | 한 건이 뜻하는 것 | 담는 내용 |
|------|-------------------|-----------|
| **1. 분석** | 프로젝트를 한 번 분석한 기록 | 커밋 번호, 분석 시각, 상태, 찾은 화면 수, 쓴 토큰 |
| **2. 화면** | 화면 하나 (라우트 하나) | 경로(`/products/:id`), 제목, 화면 파일, 로그인 필요 여부, 출처(코드) |
| **3. 요소** | 화면 안의 버튼 · 입력 · 링크 하나 | 종류, 이름, 셀렉터, 코드 위치(파일과 줄), 확인 상태 |

단계 옆에 붙는 것 두 가지.

| 이름 | 내용 | 따로 두는 이유 |
|------|------|----------------|
| **전환** | 어느 화면에서 어느 화면으로, 무엇을 눌러서 가는가 | 화면 둘을 잇는 정보라 단계에 넣을 수 없다 |
| **사용자 편집** | 화면별 제외 표시와 메모 | 다시 분석해도 지워지지 않게 한다 |

정해 둔 규칙.

- **화면은 경로로 구분한다.** 다시 분석해도 경로가 같으면 같은 화면이다.
- **요소는 화면 안에 목록으로 넣는다.** 항상 화면 단위로 읽고 쓰므로 따로 테이블을 만들지 않는다.
- **요소의 확인 상태는 세 가지다.** 코드에서 뽑은 직후는 "미확인", 그 셀렉터를 쓴 테스트가 통과하면 "확인됨", 요소를 못 찾아 실패하면 "실패". 코드만으로는 실제 화면을 알 수 없어서 실행 결과로 확인한다.
- **출처를 남긴다.** 지금은 모두 "코드"다. 나중에 사이트 탐색을 붙이면 같은 화면에 "사이트"에서 본 정보를 더한다. 그때 구조를 바꾸지 않아도 된다.
- **사라진 화면은 지우지 않는다.** "코드에서 사라짐"으로 표시만 한다.

## 4. 해야 할 일

위에서부터 순서대로 한다. 각 묶음이 끝나면 눈으로 확인할 수 있는 결과가 있다.

### 묶음 1. 화면 목록이 나온다

| # | 할 일 |
|---|-------|
| 1 | 프로젝트 설정에 **분석할 소스 저장소**(주소, 브랜치, 토큰)를 넣을 수 있게 한다. 지금의 저장소 연결은 테스트 코드용이다 |
| 2 | 소스 저장소를 복제하고 커밋 번호를 읽는다. 기존 복제 기능을 쓴다 |
| 3 | 저장 구조의 테이블을 만든다 (분석, 화면, 전환, 사용자 편집) |
| 4 | 규칙으로 화면을 찾는다. Next.js는 폴더 구조에서, React Router는 라우트 정의 파일에서 |
| 5 | 분석 시작 버튼과 진행 상황을 화면에 보여 준다 |

확인: AI-TestOps 자신(`apps/web`)을 분석해서 화면 10개가 모두 나온다.

### 묶음 2. 요소와 전환이 채워진다

| # | 할 일 |
|---|-------|
| 6 | LLM이 화면 파일을 읽고 내놓을 결과 형식을 정한다 |
| 7 | 화면 파일을 LLM에 보내 요소와 링크를 뽑는다. 파일에 없는 글자는 버린다 |
| 8 | 파일이 안 바뀌었으면 LLM을 부르지 않게 한다 |
| 9 | 뽑은 속성으로 셀렉터를 만든다. 우선순위는 `data-testid` → 역할과 이름 → 라벨 → 입력 안내 글자 → 글자 |
| 10 | 화면, 요소, 전환을 DB에 반영한다. 다시 분석해도 제외와 메모가 남아야 한다 |
| 11 | 저장된 내용을 내주는 조회 API를 만든다 (다음 단계인 그래프 화면이 쓴다) |

확인: 로그인 화면의 입력 두 개와 버튼이 셀렉터와 함께 나온다. 같은 커밋을 다시 분석하면 LLM 호출이 0이다.

### 묶음 3. 테스트 생성에 쓰인다

| # | 할 일 |
|---|-------|
| 12 | 테스트를 만들 때 화면 정보를 AI에 넘긴다. 저장된 셀렉터만 쓰게 한다 |
| 13 | 만들어진 테스트의 셀렉터가 저장된 것인지 대조하고, 아닌 것은 검토 화면에 표시한다 |
| 14 | 어느 테스트가 어느 화면의 셀렉터를 썼는지 기록한다 |
| 15 | 채팅에서도 화면 정보를 쓸 수 있게 도구를 추가한다 |

확인: 화면을 지정해 만든 테스트의 셀렉터가 모두 저장된 것이다.

### 묶음 4. 실행 결과로 확인한다

| # | 할 일 |
|---|-------|
| 16 | 테스트가 끝나면 그 테스트가 쓴 요소의 확인 상태를 바꾼다 |
| 17 | 대상 2종의 화면과 요소를 손으로 정리해 두고, 분석 결과와 비교한다 |

확인: 일부러 틀린 셀렉터를 넣으면 그 요소가 "실패"로 바뀐다.

## 5. 다 됐다고 보는 기준

- 대상 2종에서 화면의 90% 이상을 찾는다.
- 화면을 지정해 만든 테스트 10건 중 6건 이상이 손대지 않고 통과한다. 분석 없이 만든 10건과 나란히 비교한다.
- 같은 커밋을 다시 분석하면 LLM 비용이 들지 않는다.
- 다시 분석해도 제외와 메모가 남는다.

## 6. 먼저 정할 것

| 정할 것 | 제안 |
|---------|------|
| 검증에 쓸 대상 2종 | 하나는 AI-TestOps 자신(`apps/web`). 다른 하나는 React나 Next.js로 만든 프로젝트. 경주GO는 Flutter라 코드 분석 대상이 아니다 |
| 분석을 언제 돌리나 | 소스 저장소가 연결돼 있으면 등록할 때 자동으로, 이후에는 버튼으로 |
| 지원하지 않는 프로젝트 | 분석은 실패로 끝내고 이유를 보여 준다. 테스트 생성은 지금 방식대로 계속 된다 |

## 7. 나중에 할 것

- **사이트 탐색.** URL을 열어 실제 화면을 살피고, 코드에서 뽑은 정보와 맞춰 본다. `analyze.js`를 다시 쓴다.
- 화면을 캔버스에 그리는 앱(Flutter Web 등) 지원.
- React Router, Next.js 외의 프레임워크.
