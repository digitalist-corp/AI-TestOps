# AI-TestOps AI 개선안

> 작성: 장준호(PM · FE) · 2026-09-22 · 기준: 현 AI 코드(main `a3688d2`), 현업(부장님) 피드백, 프로젝트 차터 v1.6
>
> **한 줄 요약** — Spring `api`는 **손과 금고**(권한 · 실행 · 키), Python LangGraph 서비스는 **두뇌**, 실패 · 수정 이력 DB는 **기억**.
> 흩어진 AI 기능을 하나의 흐름으로 묶어 **"말로 요청 → 작성 → 실행 → 실패 분류 → 수정 → 승인 → 실패 감소"** 루프를 만든다.

## 1. 왜 바꾸는가

### 1.1 현업 피드백 → 개선 요구

| 피드백 | 의미 | 이번 개선안의 대응 |
|--------|------|--------------------|
| 대상 사이트 필요 | 자기 자신이 아닌 실제 사이트를 고객처럼 테스트해 봐야 함 | 대상 사이트 등록 + Playwright MCP로 **실제 DOM을 보고** 작성 (흐름 A) |
| 사이트 기준 시나리오 · 케이스 AI 자동 작성 | 설명만 보고 쓰면 셀렉터가 틀림 | Playwright Test Agents(planner · generator)로 계획 · 생성 |
| 말로만 테스트 시키기 · 점검 보정 | 코드 없이 지시하고, AI가 돌려보고 스스로 고쳐야 함 | 채팅 tool calling: **"만들고 돌려줘" 한 문장** → 실행 → healer · fix 노드 보정 |
| 테스트 실행 후 오류 → 바로 AI | 실패가 나면 사람 클릭 없이 즉시 이어져야 함 | 실행 실패가 **흐름 B의 시작 이벤트** → 분류 · 수정안까지 자동, 반영만 승인 |

### 1.2 현재 AI 구조(As-Is)와 문제점

| 기능 | 실행 위치 | 파일 수정 / 실행 | 한계 |
|------|-----------|------------------|------|
| AI 채팅 | api 프로세스 | ✕ / ✕ | 실행 요약 3개 값(상태 · 통과 · 실패 수)만 받음, 도구 호출 없음 |
| AI 분석 | api 프로세스 | ✕ / ✕ | 로그 끝 2,500자로 건별 분석만 |
| AI 테스트 생성 | api 프로세스 | 제안 / 부트스트랩 1회 | 승인 후 실행은 수동, 실제 화면을 보지 않음 |
| 에디터 수정 도움 | api + 일회용 컨테이너 | 제안 / 검증 1회 | 끝나면 원본 복원 — 반영은 사람이 따로 |
| CODE_FIX | AI 러너(`run.js`) | 컨테이너 안 / 최대 5회 | `tests/**`만 수정, 앱 코드 불가 |

모든 호출은 `LlmGatewayService` → Claude · GPT REST 단발 호출이다. 키는 관리자 공용 1개(AES-GCM 암호화), AI 러너는 api 내부 프록시를 경유한다.
안전장치: 경로 규칙 → 하드 게이트 → 정량 한도(30줄 · 2파일) → 자동 적용 OFF → 사후 검증 · 자동 되돌림.

- **단계가 끊겨 있다** — 생성 · 실행 · 분석 · 수정 · 커밋마다 사람이 클릭해야 다음으로 넘어감
- **채팅이 아무것도 못 한다** — 파일 · 실행 · DB에 접근할 경로가 없음
- **실패의 성격을 모른다** — 테스트 문제 / 앱 버그 / 환경 문제를 구분하지 못하고, 앱 코드는 고칠 수 없음
- **건별로만 본다** — 같은 원인의 실패를 묶지 못하고, 과거에 성공한 수정을 다시 쓰지 못함
- **루프가 굳어 있다** — `run.js`에 5회 · 파일 전체 교체 고정, 프롬프트 하드코딩, 결과는 main에 직접 반영(PR 없음)

## 2. 개선 방향

### 2.1 AI 방식 — 하이브리드 채택

| 방식 | 설명 | 판단 |
|------|------|------|
| 워크플로 그래프 | 단계 고정, 노드 안에서만 LLM | 통제 · 승인이 쉬움, 유연성 낮음 |
| 자율 에이전트 | LLM이 도구를 골라 스스로 반복 | 유연하지만 예측 · 비용 통제가 어려움 |
| **하이브리드 (채택)** | 큰 흐름은 그래프, 생성 · 수정 노드 안에서만 에이전트 | 기존 게이트 철학과 일치, 단계가 대시보드에 보임 |

- **결정적인 일은 코드로, 판단만 LLM으로** — 실패 묶기 · 수치 계산은 코드, 원인 분류 · 수정 · 요약만 LLM
- **반영은 항상 사람 승인** — AI 결과는 `ai/{jobId}` 브랜치 + PR로만 나가고 main 직접 반영은 없앰
- **키 · 권한은 api 한 곳** — ai-service는 키 없이 api의 LLM 프록시와 도구만 호출

### 2.2 목표 흐름(To-Be) — 두 개의 입구, 하나의 루프

```text
A. 말로 요청   "로그인 실패 케이스 만들고 돌려줘"
               → 대상 사이트 DOM 관찰 → 시나리오 계획 → spec 생성 → [승인① 시나리오] → 실행 → 루프로
B. 실행 실패   수동 · 예약 · CI 실행 실패 → 자동으로 루프 시작
공통 루프      결과 수집 → 실패 묶기 → 분류(테스트 / 앱 버그 / 환경) → 수정(테스트 or 앱 코드)
               → 재실행 검증 → [승인② 수정안] → 브랜치 커밋 → [승인③ PR] → 전체 재실행 · 측정
               → 실패 감소 확인 → 남은 실패 반복 → 클린
```

## 3. 아키텍처

```text
[Web / Mobile]  ← SSE: 진행 상황 · 승인 요청
      │
[Spring api]  권한 · DB · docker · Git 독점 · 승인 게이트 · API 키 보관 · LLM 프록시 (기존 유지)
      │ ↑  REST / MCP 도구 호출
[ai-service (Python, 신규 상주 컨테이너)]  LangGraph 오케스트레이터 · 체크포인트 (키 · 파일 직접 접근 없음)
      │ ↑  api 경유 읽기 / 쓰기
[PostgreSQL]  기존 테이블 + 실패 · 수정 이력 + LangGraph 체크포인트
[일회용 러너 / AI 러너]  테스트 실행 · 수정 검증 · Playwright MCP · Test Agents
[외부 LLM]  Claude / GPT — 판단 · 생성만 (모델은 서버에 없음)
```

| 구성 | 형태 | 역할 |
|------|------|------|
| Spring api | 기존 유지 | 도구 제공 · 승인 게이트 · docker · Git 독점 · LLM 프록시(키 보관, 사용량 · 비용 기록 단일화) |
| ai-service | 신규 Python 상주 컨테이너 (프로젝트별이 아닌 중앙 1개) | LangGraph 그래프 실행 · 체크포인트, 실패 · 수정 이력 읽기/쓰기(api 경유) |
| 러너 / AI 러너 | 일회용 (기존 재사용 + 확장) | 테스트 실행 · 수정 검증 · Playwright MCP |
| 외부 LLM | API | 판단 · 생성만. 공급자 교체 시 api만 수정 (BYOK · 사내 LLM은 향후 옵션) |

**api가 노출할 도구**: `generate_scenario` · `run_tests` · `get_results` · `analyze_failure` · `classify_failure` · `fix_test` · `fix_app` · `open_pr`
— 기존 서비스를 재사용하고, Spring AI `@McpTool`로 노출하면 외부 에이전트에서도 같은 도구를 쓸 수 있다.

> [AI Integration Architecture](./ai-integration-architecture.md)에서 기각한 것은 "프로젝트별 상시 AI 서버"다. ai-service는 여러 프로젝트 요청을 큐로 처리하는 **중앙 서비스 1개**이며, 실행 · 검증은 지금처럼 일회용 컨테이너에서 한다.

## 4. LangGraph 루프 설계

| # | 노드 | 하는 일 | 주체 |
|---|------|---------|------|
| ① | ingest | 새 실행 결과 → 실패 기록 적재 | 코드 |
| ② | cluster | 오류 메시지 정규화(숫자 · ID · 시간 제거) → 오류 유형으로 묶기 | 코드 |
| ③ | prioritize | flaky 제외, 영향 큰 오류 유형부터 (이력 집계) | 코드 |
| ④ | classify | 테스트 문제 / 앱 버그 / 환경 문제 분류 + 근거 | LLM |
| ⑤ | recall | 같은 오류 유형에서 과거에 **성공한 수정** 조회 → 프롬프트에 포함 | 코드 |
| ⑥ | fix | 수정안 생성 + 컨테이너 검증 (기존 CODE_FIX · healer 재사용) | LLM + 러너 |
| ⑦ | approve | interrupt → 웹 · 모바일 승인 (Postgres 체크포인트로 대기, 재시작 후 재개) | 사람 |
| ⑧ | pr_and_run | `ai/{jobId}` 브랜치 커밋 · PR → 전체 재실행 | 코드 |
| ⑨ | measure | 실패 수 · 오류 유형 수 · flaky 비율 전후 비교 → 이력 DB에 기록 | 코드 |
| ⑩ | decide | 개선 중 → ③ / 클린 → 종료 / 개선 정체 2회 · 예산 초과 → 사람에게 | 코드 |

- **기억의 연결 고리** — ⑤ recall(과거 성공 수정을 다음 수정에 사용) · ⑨ measure(결과를 다시 기록). 돌수록 "AI 수정 지식"이 쌓이고 실패 곡선이 내려간다.
- **실패 · 수정 이력 DB** — 기존 PostgreSQL 관계형 테이블. 실패 기록 · 오류 유형 · 수정 시도(`ai_job`) · 결과(해결 / 부분 해결 / 회귀) · 커밋 · PR을 오류 유형 키로 연결한다.
- **"클린" 판정** (수치는 팀 합의) — 열린 오류 유형 0 · flaky 비율 기준 이하 · 최근 N회 실행 회귀 0 · 게이트 위반 0
- **승인 지점 3곳** — ① 시나리오 확정 ② 수정안 반영 ③ PR 생성. **정지 조건** — 최대 반복 · 비용 예산 · 개선 정체

## 5. 사용할 기술과 함께 해야 할 일

| 영역 | 기술 | 용도 |
|------|------|------|
| 오케스트레이션 | LangGraph (Python) + PostgresSaver | 그래프 실행, interrupt 승인, 재시작 후 재개 |
| 테스트 생성 · 치유 | Playwright Test Agents (planner · generator · healer, 1.56+) | 실제 사이트 기준 계획 · 생성 · 자동 치유 |
| 브라우저 관찰 | Playwright MCP (또는 Playwright CLI) | 접근성 트리로 실제 DOM 확인 |
| 앱 코드 수정 | OpenHands SDK 또는 Claude Agent SDK | 샌드박스 코딩 에이전트, 권한 · hooks 통제 |
| 도구 노출 | Spring AI `@McpTool` | api 기능을 MCP 도구로 제공 |
| 평가 · 관측 | promptfoo · Langfuse | 프롬프트 평가, 에이전트 실행 추적 · 비용 |
| 대시보드 | React + ECharts (+ GraphQL 조회) | 실패 추이 · 오류 유형 맵 · AI 수정 지식 · 에이전트 타임라인 |

- **Playwright 1.53 → 1.56+** 업그레이드 (Test Agents 필요, `RuntimeVersions` 수정) — 흐름 A의 전제라 가장 먼저
- **하드 게이트 재정의** — healer의 `test.fixme()`는 통과용 꼼수가 아니라 "앱 버그 의심" 신호로 분류
- **경로 정책 분리** — `tests/**`와 별도로 앱 코드(`src/**` 등) 허용 목록 · 한도
- **main 직접 푸시 → 브랜치 + PR**, PR에서 자체 회귀 게이트 실행
- **러너 격리 보강 (선행)** — 외부 통신 제한, root 금지, CPU · 메모리 · 프로세스 수 제한, `docker.sock` 차단
- **프롬프트 코드 분리** (파일 · DB로 버전 관리 · 평가), **로그 · 진행 상황 SSE 전환** (엔드포인트는 이미 있음)

## 7. 예상 질문

- **왜 Python?** LangGraph 원본이라 interrupt · 체크포인트 등 기능과 자료가 가장 풍부하다. api는 건드리지 않고 옆에 붙여 리스크가 작다.
- **AI가 서버에 있나?** 아니다. 모델은 외부 API, 흐름은 Python 컨테이너, 실행은 일회용 컨테이너다.
- **무한 루프는?** 최대 반복 · 비용 예산 · 개선 정체 조건으로 멈추고 사람에게 넘긴다.
- **자동으로 main에 반영?** 아니다. 항상 브랜치 + PR, 사람 승인 필수다.
- **기존 CODE_FIX는?** 버리지 않고 ⑥ fix 노드의 도구로 재사용한다.
