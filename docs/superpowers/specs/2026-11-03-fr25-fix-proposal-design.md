# FR-25 실패 실행 → 수정 제안 카드

개발계획서 v2 5주차 D-01(작업 생성기)·D-07(보고 문구)의 첫 조각. 정기 점검(D-05)·작업 큐 화면(D-04)·SSE(D-02)는 다음 PR이다.

## 왜

지금은 실패한 테스트를 고치려면 사람이 AI 분석 탭이나 채팅에서 직접 작업을 만들어야 한다. 목표는 "사용자가 시키지 않아도 실패에서 작업이 생기는 것"이다. 다만 AI가 알아서 고치기 시작하지는 않는다. **"이렇게 고칠게요. 진행할까요?"라고 묻는 카드만 뜨고**, 사람이 진행을 눌러야 기존 AI 수정 작업(CODE_FIX)이 돈다. 결과도 지금처럼 검토 → 승인을 거쳐야 반영된다.

## 정한 것 (사용자 결정)

- 카드는 묻기만 한다. 진행을 눌러야 AI 수정이 시작된다.
- "어떻게 고칠지" 문장은 **AI 없이 오류 규칙으로** 만든다. AI 키가 등록된 서버에서만 그 문장을 AI로 짧게 다듬는다. 다듬기가 실패하면 규칙 문장을 그대로 둔다.
- 문장은 사용자 가이드처럼 비전공자가 읽는 말투로 쓴다.

## 동작

1. 테스트 실행이 **FAILED**로 끝나면 실패한 spec마다 제안 하나를 만든다. 한 실행에서 최대 3개까지만 만든다.
   - 제외: `AI_POST_APPLY` 실행, AI 첫 테스트 실행(케이스 제목이 `AI 초기 케이스`로 시작. 그 흐름이 스스로 2번 고친다), ERROR 실행(러너·환경 문제라 코드 수정 대상이 아님).
   - 중복: 같은 프로젝트·같은 spec에 열린 작업(PROPOSED·PENDING·RUNNING·DIFF_READY·NEEDS_REVIEW)이 있으면 만들지 않는다.
   - 상한: 프로젝트당 하루(서버 시각 자정 기준) 자동 제안 20개.
2. 제안은 `ai_jobs` 행이다. `job_type=CODE_FIX`, `status=PROPOSED`, `requested_by=null`(자동 생성 표시), `failed_execution_id`, `target_spec_path`.
   - `summary` = 무엇이 문제인지 한 줄 (`CoverageRules.explain` 재사용). 예: "'결제하기' 버튼을 찾지 못했습니다 · 장바구니 > 결제".
   - `instruction` = 어떻게 고칠지 한 줄. 진행하면 이 문장이 그대로 CODE_FIX 지시문이 된다.
3. 제안이 생기면 모든 사용자에게 알림 `FIX_PROPOSED`(INFO)를 보낸다. 누르면 그 실행의 결과 화면으로 간다.
4. **진행** `POST /api/ai-jobs/{id}/proceed`: PROPOSED일 때만 받는다. AI 키가 없으면 400. PENDING으로 바꾸고 콜백 토큰을 새로 발급한 뒤 기존 `runAsync`를 돈다.
5. **닫기** `POST /api/ai-jobs/{id}/dismiss`: PROPOSED → CANCELED.

### 규칙 문장

| `explain` 결과 | 고칠 방법 |
|---|---|
| 요소를 찾지 못함 / 여러 개라 모호함 | 구조 지도에서 찾은 이름표로 셀렉터를 바꿔 고칠게요. |
| 값이 기대와 다름 | 화면에 실제로 보이는 값을 확인해, 기대값이 바뀐 거라면 확인 조건을 고칠게요. |
| 도착 주소가 기대와 다름 | 실제로 이동하는 주소에 맞게 이동 확인을 고칠게요. |
| 화면을 열지 못함 | 사이트 주소와 대기 조건을 확인해 화면 열기 단계를 고칠게요. |
| 그 밖 | 실패 기록을 보고 멈춘 단계를 고칠게요. |

AI 다듬기: 시스템 프롬프트로 "원인 한 줄과 고칠 방법 한 줄을 존댓말 120자 이내로" 요청한다. 입력은 규칙 문장, 케이스 이름, 오류 원문 앞 1,500자다. 결과가 비었거나 300자를 넘으면 버린다. 사용량 기능명은 `FIX_PROPOSAL`이다. 실행 스레드를 잡지 않도록 `aiJobExecutor`에서 비동기로 돈다.

## 화면

- **결과 탭**: "실패한 케이스" 위에, 고른 실행의 PROPOSED 제안을 카드로 보여 준다. AI를 끄더라도 보인다.
  - 카드 내용: 제목 "이렇게 고칠까요?", 문제 한 줄, 고칠 방법, 파일 이름.
  - AI가 켜져 있으면 **진행** / **닫기** 버튼을 둔다. 진행하면 "AI 검토 탭에서 결과를 확인하세요"라는 안내를 띄운다.
  - AI가 꺼져 있으면 **닫기** 버튼과 "AI를 켜면 이 방법대로 자동으로 고쳐 볼 수 있어요" 안내를 둔다.
- **AI 검토 탭**: 상태 이름에 `PROPOSED: '수정 제안'`을 추가한다. 목록에는 기존처럼 최근 작업으로 보인다.
- **알림 창**: kind로 화면이 달라지지 않으면 그대로 둔다.

## 하지 않는 것

정기 점검, 작업 큐 화면, SSE, 새 커밋 감지는 이번 범위가 아니다. 같은 실패 유형을 묶는 유사 작업 검사도 하지 않는다. 중복 검사는 spec이 같은지만 본다.

## 판단 (내 결정)

- 새 표 대신 `ai_jobs`에 상태 하나만 추가한다. FR-26 작업 큐가 같은 목록을 그대로 쓴다. 예전 Hibernate 자동 생성 DB에 남은 `ai_jobs_status_check` 제약이 새 값을 막아서, V9에서 이 제약을 지운다(Flyway 기준선에는 원래 없음).
- 리포트의 spec 경로는 testDir 기준이라, 제안에는 프로젝트 기준 경로(`tests/…`)로 바꿔 저장한다.
- CODE_FIX가 spec 하나만 고치므로 제안도 spec 단위로 만든다. 계획서 완료 조건 "실패한 실행 하나에 작업 하나"는 실패한 spec이 하나인 보통의 경우에 그대로 맞는다.
- AI 첫 테스트 실행은 케이스 제목 접두사로 거른다. 실행에 출처값을 넘기는 길이 없어서 택한 방법이다. 출처 매개변수가 생기면 그 값으로 바꾼다.

## 검증

- `FixProposalRules` 단위 테스트: 오류 유형마다 문장이 맞는지 확인한다.
- `FixProposalService` 단위 테스트: 실패에서 제안이 생기는지, 제외·중복·상한이 지켜지는지, 진행·닫기의 상태 검사가 맞는지 확인한다.
- 승인 게이트: 진행해도 상태는 NEEDS_REVIEW까지만 간다. 자동 반영은 기존 `aiAutoApplyEnabled`(기본 false) 경로 그대로다.
